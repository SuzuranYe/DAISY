# DAISY v1.6.2 正式发布计划

- 目标版本：v1.6.2
- 发布性质：正式稳定版
- 前一稳定标签：v1.6.0
- 阶段版本：v1.6.1 未建立标签，只保留实施与测试历史
- 数据库兼容基线：v1.4.1/schema 3 FULL 封存快照
- 测试证据：[v1.6.2 测试记录](Spec_DAISY_V1_6_2_Test_Record.md)

## 一、发布目标

v1.6.2 将 v1.6.1 阶段完成的 UI、交互、统一扫描、核验、数据库解析、外部工具隔离与
报告改进收敛为正式版。发布不是单纯修改版本号：只有完整自动化测试、v1.4.1 FULL 专项、
静态审计和远端发布核验全部通过，才能建立 `v1.6.2` 标签。

本版沿用 v1.6.0 的数据与恢复契约，不升级数据库结构。GUI 和文案可以调整，封存数据库的
只读兼容边界、旧脚本协议和结果语义不能被 UI 改动带偏。

## 二、安全范围

- 所有读取、写入和测试产物限于仓库工作区或系统临时目录。
- 不读取真实档案，不启动真实扫描，不调用真实 ExifTool、ffprobe、7-Zip、rawpy、smartctl
  或硬盘检测；外部工具行为只使用测试替身和测试自己创建的子进程。
- 不枚举、附加、复用、终止或修改用户已有进程。
- 不访问本轮未明确授权的工作区外数据库。v1.4.1 专项使用仓库内冻结金样契约与测试生成的
  schema 3 FULL 数据库。
- 不清理用户文件；测试临时目录由对应测试创建并回收。

## 三、不可变兼容边界

### 3.1 数据结构与旧入口

- `SCANNER_VERSION` 与 STG `APP_VERSION` 更新为 `1.6.2`；DBS schema 3、统一扫描 schema 4、
  STG archive schema 3、元数据 profile 7 和 `daisy-resume-v1` 不升级。
- `full-scan` 与 `quick-scan` 继续作为冻结的 v1.4.1/schema 3 兼容入口；统一 GUI 使用
  `scan`，但不得改变旧入口的参数集合和生成语义。
- v1.4.1 已封存 FULL 数据库只读使用；不得迁移、补列、回写或接管其未完成快照。
- schema 3 缺少 schema 4 能力时显示 `NULL`／不可用，不得伪装为 0、空记录或成功。

### 3.2 冻结源码

以下文件相对 v1.6.0 标签必须保持无差异：

- `Script/Module/Script_DAISY_Module_DBS_11_Full_Scan.py`
- `Script/Lib/Script_DAISY_Lib_DBS_04_Diff.py`
- `Script/Lib/Script_DAISY_Lib_DBS_05_Reader.py`

若完整回归暴露问题，应优先修正调用层、测试或文档。除非出现可以证明的兼容缺陷并重新审查
数据契约，否则不得为通过测试而修改上述文件。

## 四、发布验收矩阵

### 4.1 完整自动化套件

在仓库根目录运行：

```powershell
python -B -W error -m unittest discover -s .\Script\Test -p "Script_DAISY_Test_*.py" -q
```

准入条件：退出码 0，failure 0，error 0，warning 作为错误处理；不得跳过 Windows 上本应
运行的真实 Tcl/Tk 用例。测试范围包括 GUI 字体／缩放／窗口组合、CLI、扫描状态机、工具
隔离与恢复、Diff、核验、解析、问题报告和 STG。

### 4.2 v1.4.1 FULL 专项

专项必须覆盖：

1. 读取仓库内 `DBS_v1_4_1_Schema3_Contract.json`，核对来源版本、Git 标签、冻结 DDL 摘要、
   表集合与 schema 3 能力声明。
2. 生成 `source_version=1.4.1`、`scan_kind=full`、`hash_coverage=full`、
   `metadata_storage=complete` 的封存金样，并验证统一 Reader 的身份、能力和只读打开方式。
3. 覆盖 3→3、3→4、4→3、4→4 Diff；方向必须正确，缺失能力不得被判断为相同。
4. 覆盖统一核验的 schema 3 投影、旧兼容入口和分板块报告；未执行能力使用 `NULL`。
5. 覆盖数据库解析的识别、方案生成、模块投影、人读名称、CLI 与真实写出逻辑；schema 3
   可用模块字段稳定，缺失模块明确不可用。
6. 在每项只读操作前后比较输入数据库字节 SHA-256、大小和修改时间；三者均不得变化。

专项不声称替代真实用户库抽样。此前 v1.6.1 记录中的工作区外真实库结果只作历史证据；
本次发布结论以仓库内可复现的冻结契约和合成 FULL 金样为准。

### 4.3 静态与文档审计

- 对全部受跟踪 Python 文件执行 `compileall`，对 PowerShell 脚本执行解析器检查。
- 文本文件必须为 UTF-8 无 BOM、LF；不得引入 CRLF、UTF-16 或非法 UTF-8。
- 检查 README 和 Spec 中的相对 Markdown 链接均存在，且不使用 Wiki／Obsidian 双方括号链接。
- 检查版本常量、README、技术规格、版本演进和发布记录均指向 v1.6.2；v1.6.1 只出现在
  明确的历史上下文中。
- 检查冻结源码与 v1.6.0 无差异，检查工作树无未跟踪测试残留。
- 检查 `git diff --check`、单元测试资源回收和发布前分支关系。

## 五、缺陷处理与复测规则

- 完整套件出现失败时，先保存失败名称、退出码和日志末尾，再定位最小原因。
- 仅修改与失败直接相关的代码或测试，不借机重构无关逻辑。
- 修复后先运行最小相关用例，再重新运行完整套件；完整套件未重新通过不得发布。
- 文档或版本声明的最终改动至少重跑文档／版本相关用例和静态审计；若影响被完整套件读取的
  权威文本，则重新运行完整套件。
- 真实 Tcl/Tk 崩溃、挂起、资源泄漏或 native 弹窗均为发布阻断，不能按偶发问题忽略。

## 六、发布流程

仅在全部门禁通过后执行：

1. 更新测试记录中的实际命令、用例数、耗时、结果和限制。
2. 在 `Codex` 分支审查最终差异并创建发布检查点提交。
3. 推送 `Codex`，将 `main` 以 `--ff-only` 快进到同一提交并推送。
4. 在该提交创建注释标签 `v1.6.2`，标签说明为 `DAISY v1.6.2`，随后推送标签。
5. 通过本地引用和远端引用确认 `Codex`、`main`、`v1.6.2^{}` 指向同一提交。
6. 确认工作树干净，并在最终交付中列出提交、标签、完整回归和兼容专项证据。

任一门禁失败时停止发布，保留 `main` 和远端稳定标签不变；不得创建指向失败状态的标签。
