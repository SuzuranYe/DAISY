## 一、版本结论与目标

本轮不再命名为 v1.5.2。原因不是界面改动数量，而是计划同时涉及：

- 续传状态机、暂停和跨重启恢复；
- 哈希读取的工作进程隔离、timeout、重试和性能证据；
- 新运行 session、尝试历史和可选格式校验证据；
- v1.4.1 旧数据库读取适配与跨版本 Diff；
- DBS-21／31／32 的语义复审；
- DBS 信息架构和脚本编排调整；
- DBS-41 从“结果报告导出”重构为“数据库解析”；
- Issues 和人读报告的重新设计。

这些内容可能需要新的 SQLite schema 和 data contract，属于数据能力版本，使用 v1.6.0
更诚实。v1.5.1 保持已发布基线，不回写、不重打标签。

v1.6.0 的最终目标是：在不牺牲证据完整性和 v1.4.1 旧库兼容的前提下，让扫描可以安全
暂停与恢复，让卡死读取可以受控处置，让对比和核验结论重新经过验证，并让普通用户只需
理解“扫描、对比、核验、解析”四个动作。

## 二、不可违反的约束

### 2.1 工作区与进程隔离

1. 所有源码、文档、夹具、测试输出和临时文件必须位于固定工作区
   `C:\Cytus\Project\Dev_Proj\Workshop\DAISY` 内。
2. 测试运行时把 `TEMP`、`TMP` 和项目测试临时根显式指向工作区内
   `.test_runtime\v1_6_0\<run-id>`；不得把项目测试数据写到系统临时目录。
3. 不读取测试夹具之外的真实档案，不访问旧数据库记录的工作区外源路径。
4. 不运行真实物理硬盘检测、SMART 采集、WinGet 安装、管理员重启或缓存清理。
5. 不枚举、不停止、不挂接、不复用其它正在运行的进程；禁止按进程名执行
   `taskkill`、`Stop-Process` 等操作。
6. 需要模拟卡死或外部工具时，只启动工作区内受控替身，并只通过本测试持有的精确
   `Popen`／PID 句柄回收其子进程树。
7. 用户的 `TEMP\` 目录保持未跟踪、只读观察，不删除、不改名、不加入提交。

Python 和 PowerShell 读取自身运行库属于运行时必要访问，但项目数据、输入和输出仍须
遵守工作区边界。

### 2.2 数据只读与发布安全

1. 源档案始终只读；扫描、对比、核验、解析和报告不得修改源文件。
2. 已封存 SQLite 始终只读；不执行迁移、补列、`VACUUM`、journal 模式切换、临时索引
   或任何写事务。
3. 所有新产物先写入已验证位于目标目录内的唯一 staging，再做完整性检查并 no-clobber
   原子发布；失败、取消或冲突不得覆盖旧产物。
4. 删除只允许清理由本次任务创建且已验证处于 staging 内的临时文件；不得使用宽泛路径、
   glob 或未解析变量作为删除目标。

### 2.3 v1.4.1 长期兼容规则

“兼容 v1.4.1”在本项目中固定解释为：

- v1.6.0 及后续程序中，凡接受已封存 DBS 快照或 Diff 数据库的功能，至少必须只读支持
  v1.4.1／schema 3；
- 适用功能包括 Issues 渲染、对比、哈希核验、格式校验、数据库解析、GUI 数据库识别和
  后续新增的封存库读取功能；
- 旧库缺少 v1.6.0 新能力时，必须显示“此数据库未记录／不可用”，不能伪造为 0、空值、
  正常或内容未变化；
- v1.6.0 不原地升级旧库。每项兼容测试前后计算输入数据库完整 SHA-256，并断言相同；
- 该保证是“新程序读取旧数据库”，不反向保证 v1.4.1 程序读取未来新 schema；
- v1.4.1 未完成 `.partial.sqlite` 不属于无条件兼容对象。只能先做只读诊断，若设计恢复
  工具则必须复制到新工作产物后转换，绝不原地尝试续传。

此规则已经写入现行[技术规格](Spec_DAISY_Technical.md)的版本与兼容性章节，未来版本
不得在没有兼容测试和明确版本说明的情况下撤销。

## 三、确认后的产品信息架构

### 3.1 普通用户入口

DBS 主界面简化为四个入口：

| 入口 | 用户问题 | 内部能力 | 旧 CLI 兼容 |
|---|---|---|---|
| 扫描 | 我要建立一个档案快照 | DBS-11 Full、DBS-12 Quick | 保留 `full-scan`、`quick-scan` |
| 对比 | 两个快照之间发生了什么 | DBS-21 | 保留 `diff` |
| 核验 | 当前文件是否仍与快照一致、结构是否可读 | DBS-31、DBS-32 | 保留 `check-hash`、`check-format` |
| 解析 | 数据库里有什么，我要导出哪些内容 | DBS-41 | 保留 `export-report` 兼容入口；新增 `parse-db` |

普通界面不要求用户先理解 DBS 编号。编号继续用于脚本名、CLI、日志、测试和技术文档，
从而避免破坏现有自动化。

### 3.2 扫描

“扫描”先选择模式，再选择该模式可用功能。

完整扫描（Full）的基线含义保持不变：

- 完整内容 SHA-256；
- 完整规范化元数据和 raw payload；
- File ID；
- 现有独立哈希抽验；
- 最终复扫、完整性检查和封存。

格式校验是 Full 的附加选项，不改变 Full 基线：

- `关闭（默认）`：结果和文件名基线与 v1.5.1 Full 语义一致；
- `抽样校验`：默认抽样比例沿用现有格式校验页的 10%，允许设置；
- `全部校验`：对所有具备校验器的文件执行结构检查。

Quick 保持只登记目录与 stat、不读取内容、不调用外部解析工具。选择 Quick 时内容哈希、
元数据和格式校验必须禁用并显示原因，不能启用这些功能后仍命名为 Quick。

文件名规则：

- 默认关闭格式校验：继续使用 `根标签_Full_日期_时间_XXXXXXXX.sqlite`；
- 抽样格式校验：可增加 `Fmt-Sample`；
- 全量格式校验：可增加 `Fmt-All`；
- 精确比例、校验规则和工具版本以 config／manifest／库内证据为准，文件名不是权威；
- 新标记使用新的 `filename_layout_version`，读取 v1.4.1 layout 2 时不得靠文件名猜能力。

数据库只能记录发布 stem 与 `_<SHA256-high32-uppercase>.sqlite` 路径模式，不能记录含自身
摘要的最终文件名；否则写入文件名会再次改变数据库 SHA-256，形成自引用。实际文件名由
关闭后的发布副本摘要决定，并由 Reader 交叉核对。

格式不支持不是问题：只记录去重文件总数。已知格式损坏、截断、缺流、CRC 错误、timeout、
工具崩溃和读取错误仍要保留证据并进入 Issues。格式问题不阻止数据库完整封存；“扫描
完成”和“源文件存在问题”是两个不同状态。

### 3.3 对比

“对比”选择基准快照和对比快照，自动识别双方 schema、生成器、根目录和证据能力。

必须支持：

- v1.4.1 → v1.4.1；
- v1.4.1 → v1.6.0；
- v1.6.0 → v1.4.1；
- v1.6.0 → v1.6.0。

对比先把双方转换为带能力标记的规范化只读投影，再执行 Diff。新字段只在双方都有可比
证据时参与判断；一侧缺失时输出 `unavailable`／证据不足，不能把缺少新字段误判为内容或
元数据变化。交换新旧侧后，added／deleted、old／new 字段和结论方向必须同步反转。

需要重新验证的既有语义包括：root 自动与显式映射、移动／重命名、复制、重复哈希多重集、
硬链接、无哈希、unstable、枚举失败子树、raw payload 缺失和 metadata extraction changed。
内容维度与结构维度必须继续分开，hash missing 不能污染路径存在性结论。

### 3.4 核验

“核验”合并现有 DBS-31 和 DBS-32 的 GUI，不再单列“文件结构核验”。流程为：

1. 选择一份已封存快照；
2. 自动识别 v1.4.1／v1.6.0 能力；
3. 映射当前根目录；
4. 全量 stat 核对始终执行；
5. 可分别勾选“内容哈希”和“格式校验”；
6. 内容哈希可选抽样或全量，格式校验可选抽样或全量；
7. 两类核验共享进度、暂停、timeout、停止和报告发布，但状态与结论分别统计。

哈希核验必须在读取前后都检查 size／mtime；只有前后稳定、读取完整且独立 SHA-256 与
基准相同，才能表述为“本次核验一致”。旧库没有有效基准哈希时显示“不可核验”，不能以
stat 相同代替内容一致。

格式校验不等于逐帧或完整语义解码。报告必须说明覆盖边界。底层 `check-format` 服务和
CLI 保留，用于 v1.4.1 旧快照、自动化和组合调用，但不再作为 GUI 一级入口。

### 3.5 数据库解析

DBS-41 从“结果报告导出”更名为“数据库解析”。完整设计见
[数据库解析设计](Spec_DAISY_V1_6_0_Database_Parsing_Design.md)。确认的核心流程是：

1. 选择一个 SQLite 数据库，不手工选择快照／Diff 类型；
2. 只读识别类型、schema、生成器、封存状态、完整性和可用模块；
3. 以与硬盘候选页一致的复选卡选择模块；
4. 选择与模块兼容的输出格式；
5. 流式解析并原子发布。

快照模块至少包括：概览、Issues、文件、目录、逐文件哈希、照片格式化字段、视频格式化
字段、GPS、媒体流、工作文件、文档、压缩包／成员、原始载荷、错误／诊断和运行历史。
Diff 模块至少包括：概览、文件变化、目录变化、内容分组、枚举缺口和证据说明。

输出格式：

- 自包含 `Report.html`：默认人读入口，只放摘要和有限预览；
- `Report_Excel.xlsx`：人工筛选和表格分析；
- 技术 CSV：平面稳定字段和完整值；
- JSONL：嵌套结构、逐文件记录和 raw payload。

raw payload 导出按行解压 `payload_zlib`，同时校验 `uncompressed_bytes` 与
`payload_sha256`，保留 provider、provider version、profile 和文件逻辑路径。损坏载荷
必须形成明确错误；不能静默跳过，也不能把完整原始 JSON 强塞进 Excel 单元格。

“人读摘要”“完整审计”“自定义”是内容预设，不是输出格式。选择完整审计不会暗中改变
用户选择的 HTML／XLSX／CSV／JSONL。

v1.6.0 会重组 DBS 信息架构，但不得倒退已经发布的 v1.5.1 UI／体验契约。以下项目全部
视为发布阻断项；详细现行定义继续以[技术规格](Spec_DAISY_Technical.md)第 12.2～12.5
节和[v1.5.1 测试计划](Spec_DAISY_V1_5_1_Test_Plan.md)为准：

1. 设置、进度、日志和命令区继续使用固定 grid，不恢复纵向拖动柄或 `PanedWindow`。
   默认 1080p 可用工作区内，设置内容无需向下滚动；不能靠把整体字号缩得难以阅读解决。

## 四、暂停、停止与跨重启恢复

### 4.1 三种语义

| 操作 | 进程与锁 | 下次启动 | 当前文件 |
|---|---|---|---|
| 暂停／继续 | 窗口、任务身份和锁保留；不领取新工作 | 不适用 | 在安全边界暂停；同会话可保留可验证内存状态 |
| 保存进度并退出 | 提交已完成工作，关闭数据库和本任务进程，释放锁 | 主动显示恢复卡片，用户确认后继续 | 不持久化哈希器／外部进程状态，当前文件从头重做 |
| 停止任务 | 安全结束本 session，partial 为防误删继续保留 | 不主动建议恢复，但可手动选择 | 未完成文件保持可审计的未成功状态 |

“下次打开电脑可以继续”解释为下次打开 DAISY 后提供恢复入口，不默认配置 Windows 开机
自启动，也不自动开始读取。运行中关闭窗口一定确认，推荐动作是“保存进度并退出”。系统
关机通知只做尽力保存；突然断电或进程被杀也必须依靠 SQLite 事务恢复到一致边界。

### 4.2 状态机要求

状态至少能够区分：

- `running`；
- `pause_requested`（瞬时控制态）；
- `paused`／已安全保存；
- `stopped`；
- `sealing`；
- `sealed_unpublished`；
- `published`；
- `failed_recoverable`；
- `failed_terminal`。

最终枚举值和 DDL 在 schema 设计阶段冻结。不能把所有状态继续塞成 `running`，也不能先
写 `complete` 再进行可能失败的封存步骤。状态、事件、session、锁和发布文件必须形成可
验证的转换表。

### 4.3 当前文件边界

- 不序列化 Python `hashlib` 对象或 ExifTool／ffprobe／7-Zip 进程内部状态；
- 跨重启时保留已完成文件，正在处理的单个文件回到可重试状态并从头处理；
- 同会话暂停只有在已经证明恢复结果与不中断相同时才允许保留块内状态；
- 元数据和格式外部工具在无法安全挂起时，应完成当前调用或终止该受控工作进程并重试；
- 恢复后重新枚举和对账，不能只按保存的阶段号跳过源目录变化检查。

## 五、哈希 stall、timeout、重试与性能

### 5.1 动态无进展 timeout

默认公式已经确定为：

```text
max(90, ceil(size_bytes / (9 × 1024³)) × 90) 秒
```

边界：

- 0～9 GiB（含 9 GiB）：90 秒；
- 大于 9 GiB、至 18 GiB：180 秒；
- 大于 18 GiB、至 27 GiB：270 秒；
- 依次递增。

这是“最后一次成功读取新数据后的连续静默时间”，不是文件总处理时间。每次成功读到块
都重置计时。现有 30 秒只作为早期 stall 告警，不取消读取。

达到阈值先记录 `threshold_reached`，不立即等同于最终失败。GUI 提供：

- 继续等待；
- 跳过并记录；
- 停止并保留续传。

用户不选择时默认继续等待，不静默跳过、不停止。高级设置可以把自动处置改为“跳过并
记录”或“停止并保留续传”；非默认策略必须在任务开始前显示并写入运行配置。自动处置与
按钮点击使用单一原子决策，避免竞态执行两次。

“继续等待”保留阈值事件并延长当前尝试；“跳过并记录”结果是 timeout／人工策略跳过，
不能伪装成普通 skipped；“停止并保留续传”先回到一致事务边界。

### 5.2 工作进程隔离

可能永久阻塞的单文件读取必须进入本窗口创建的独立工作进程。控制进程负责：

- 心跳与最后成功偏移；
- 限频字节进度；
- 暂停和软停止；
- timeout 决策；
- 终止、等待和精确回收；
- 将结果提交到主 SQLite 事务。

不得假设 Windows 阻塞线程可以安全取消，不得按进程名杀死其它 DAISY 窗口或外部工具。

### 5.3 重试和尝试证据

续传提供：

- 仅处理 pending；
- 重试瞬时失败；
- 重试全部未成功。

确定性 unsupported 不重复；I/O 错误、timeout、工具崩溃可按策略重试。每次尝试记录
session、attempt number、工具、开始／结束、已读字节、最长 stall、结束原因和用户／预设
决策。更新当前结果前清理上一次派生行，但历史尝试证据保留，不能把旧错误与新成功混在
同一个“当前状态”中。

### 5.4 当前文件与统一进度

- 高级或视图设置增加默认关闭的“显示当前文件”；
- 枚举显示当前目录，哈希／元数据／格式／复扫／抽验显示相对文件路径；
- 窄窗口中间省略，悬停标题和文本均显示完整路径；
- 关闭开关时生产者停止发送普通 `current_item`，而不只是隐藏控件；
- 文件名事件限制在 5～10 Hz，数值进度约 1～2 Hz，GUI 轮询可保持约 80 ms 但每类只
  应用最新值；
- 不确定动画评估从 12 ms 放宽到 30～50 ms，并用 CPU／流畅度测试决定最终值；
- 开始任务后收起设置、展开进度和日志，二者填满默认 1080p 可用高度；独立日志窗口和
  小窗共享状态。

### 5.5 事后性能分析

保存受控频率的读取摘要，而不是每个 4 MiB 块无条件写库。至少可还原 bytes read、总
单调时钟耗时、stall 次数、最长 stall、首次／末次 stall、最终偏移和结束原因。

离群分析只能在同一卷、相近文件大小和类型的比较组内使用中位数、MAD 或分位数；排除
`origin=reused`。输出只能称为“读取性能异常候选”或“可疑逻辑路径／时段”，不能据此
宣称物理坏区、机械盘盘面区域或 SSD 闪存位置。

高置信度候选进入同名 `_Issues.md` 的独立章节；低置信度样本只留数据库。即使只有性能
候选，也只生成这一份 Issues，不另建竞争报告。

## 六、Issues.md 人读规则

Issues 是数据库证据的人读提炼，不是新的事实来源。

1. 顶部先给出固定板块状态表。板块至少包括“枚举问题”“哈希问题”“Exif／元数据问题”
   “格式校验问题”“读取性能异常候选”和“运行／证据问题”。
2. 每个板块使用稳定的 Markdown 二级标题，不能把不同来源的错误混在一张无分类表中。
3. 每个板块严格区分：已执行且有问题＝具体文件数，已执行且无问题＝`0`，本次未执行、
   旧库未记录或能力不适用＝字面值 `NULL`，并在旁边写明原因。不得用 `0` 代替未执行。
4. 正文在各板块内再按“需要处理”“待复核候选”“信息性诊断”排序。
5. 确定性的 unknown／unsupported／unrecognized format 不显示路径、不按扩展名展开，
   只记录去重文件总数；若这是唯一诊断，不单独生成 Issues。
6. 已知格式损坏、截断、缺流、timeout、工具崩溃和读取错误不能被上述规则隐藏。
7. `ExifTool:Main:Copy1:Warning` 等动态序号归一化为稳定字段族。
8. 汇总同时显示诊断记录数和影响文件数。
9. 普通 `[minor]` warning 与 validation 折叠；严重 warning 和异常高密度 warning 进入
   待复核候选。
10. 合并重复的“问题条目状态”和“错误明细”，同时显示路径、错误、元数据／哈希／格式
   状态与建议操作。
11. 同拍摄组聚合只作为可展开的展示推断，不替代逐文件证据。
12. 所有折叠显示总数、展示数和完整证据所在表。
13. v1.4.1 旧库使用 v1.6.0 报告器时适用同一规则；例如未记录格式校验时该板块为
    `NULL`，不能写成 `0` 或“通过”。生成前后数据库 SHA-256 不变。

固定结构示例：

```markdown
## 哈希问题

- 执行状态：已执行
- 问题文件：0

## Exif／元数据问题

- 执行状态：已执行
- 问题文件：3

## 格式校验问题

- 执行状态：NULL（本次未执行或数据库未记录）
- 问题文件：NULL
```

本轮工作区实例已经证明问题存在：76,059 个条目的旧库只有 3 个实际错误，但旧报告约
2,752 行；v1.5.1 当前报告器仍会生成约 2,757 行。2,697 个原始诊断分组将 `CopyN`
归一化后只剩 12 个。该实例只用于需求依据，不成为自动测试依赖。

## 七、数据库与兼容架构计划

### 7.1 先建立只读能力层

在修改 schema 或业务逻辑前，先建立统一数据库读取能力层。它负责：

- 识别快照／Diff／partial／未知 SQLite；
- 验证 schema、状态、必要身份和只读完整性；
- 检查实际表和列，而不是只比较版本字符串；
- 为 schema 3 和未来 schema 提供规范化投影；
- 返回 `available`、`empty`、`unavailable`、`incompatible`、`invalid` 能力状态；
- 供 Issues、Diff、核验、解析和 GUI 预览共用。

建议新增 `Script_DAISY_Lib_DBS_05_Reader.py`。最终命名在编码前按现有编号审查，但不得
让 GUI、DBS-21、31、32、41 各自保留重复且行为不同的 schema 探测 SQL。

### 7.2 新 schema 候选

预计需要升级到新的 schema（候选为 4），但编号必须在 DDL 和迁移边界审查后冻结。候选
能力包括：

- `run_sessions`：一次初始运行或恢复 session 的身份、工具、时间、配置和结束原因；
- `entry_attempts`：哈希、元数据和格式校验的逐次尝试证据；
- `read_performance`：每文件低频读取摘要和 stall 统计；
- `format_checks`：Full 可选格式校验的当前结果、校验器、工具和覆盖；
- 快照级能力／状态字段：暂停、封存、发布和性能候选摘要。

设计约束：

- 不把新状态偷偷塞入 schema 3 旧字段；
- 不逐块写入 SQLite；
- 当前结果与历史尝试分离；
- 封存库仍自描述且可完整审计；
- schema 3 适配器不依赖这些新表；
- 新库的 `min_reader_version` 如需提高必须诚实记录。

### 7.3 跨版本规范化投影

Diff 和数据库解析不直接以物理表结构作为业务接口。建立版本化投影，例如：

- snapshot identity；
- roots／directories／entries；
- valid hashes and provenance；
- normalized metadata；
- raw payload capability；
- errors／diagnostics；
- format checks；
- run／attempt／performance evidence。

每个字段携带可用性。投影版本单独记录，避免应用版本、schema、metadata profile、文件名
布局和续传契约互相替代。

## 八、脚本合并与修改方案

### 阶段 4：哈希 worker、暂停与 timeout

1. 单文件读取迁移到受控工作进程。
2. 实现 30 秒 stall 和 90 秒／9 GiB 动态 timeout。
3. 实现继续等待、跳过并记录、停止并保留续传及高级默认处置。
4. 实现同会话暂停、保存退出、停止和突然终止恢复。
5. 接入 attempt 与低频性能摘要。

检查点：永久阻塞夹具可受控结束，不留僵尸进程或损坏事务。

当前进度：第 1～3 项的哈希内核、第 4 项的哈希文件边界，以及第 5 项的 attempt／性能
摘要接入已完成。单文件读取使用本次任务持有的精确进程句柄；worker 启动握手不计入
读取 timeout，30 秒 stall 与按 `max(90, ceil(size_bytes / 9 GiB) * 90)` 计算的无进展
timeout 分离。继续等待会重置本轮 timeout 窗口，不会静默跳过；跳过、停止、暂停、崩溃
和无结果均先回收本次 worker，再原子提交当前状态与历史 attempt。哈希阶段按文件游标处理，
支持仅 pending、瞬时失败和全部未成功三种集合，当前文件事件默认关闭并按 100 ms 限频，
数值进度按 500 ms 限频。

运行生命周期的第二个子检查点也已实现：`DBS_09_Run.py` 以 no-clobber 创建 schema 4
partial 和 `<partial>.lease`，提供不写库的恢复预览、活 owner 拒绝、失效 owner 明确
接管、新 resume session、精确 lease／数据库双端心跳及失败清理。同会话 `paused` 后进程
突然退出的缺口已补齐：确认旧 lease 失效后，旧 session 先记为 abandoned，再创建新
session；不会卡在“旧 session 未结束但 paused 不可恢复”的状态。恢复和心跳严格以
`mode=rw` 打开既有数据库，不会在路径竞态中创建空库；损坏 lease 可见但只允许明确接管，
接管后再次读取 active session、状态和配置，不能把接管前预览当作写入依据。

第三个子检查点已实现 GUI／任务控制协议与哈希阶段的同会话控制循环。控制消息使用有
长度上限、严格递增序号的 UTF-8 JSONL；暂停／保存退出／停止由同一个 first-wins 原子
入口仲裁，timeout 决定还绑定当前 worker PID，旧 worker 的决定不能误用于新文件。运行
中暂停先安全取消当前 attempt 并保留 pending；暂停后继续会换用新的控制对象并从文件
起点重试；暂停后保存会以 CAS 增加 revision、结束当前 session 并建议下次恢复；暂停后
停止则进入 `stopped + manual_only`。输入读取器不关闭调用方 stdin，测试只回收自己持有
的 worker 句柄。

第四个子检查点已把同一状态编排扩展到枚举、元数据和复扫的安全边界，并提供可直接用于
生产管线的受控阶段包装。枚举暂停不会把临时半棵树发布为当前结果，继续后重跑完整对账；
元数据先完成并提交当前文件再暂停，恢复后的进度从数据库全局状态重建，不会把“剩余数”
误显示为总数；复扫提交已观察变化后可重跑。数值进度按 500 ms 限频，当前文件按 100 ms
限频且默认从生产者关闭。既有 schema 3 函数只增加末尾可选回调，默认调用及旧专项回归
保持不变。

第五个子检查点已完成 schema 4 内部生产收尾链。独立抽验不再使用无界批处理：每个文件
由本任务持有的 PowerShell `Get-FileHash` 精确进程执行，路径使用 UTF-8 令牌和 UTF-16LE
`-EncodedCommand`，并复用 30 秒 stall、90 秒／9 GiB 动态无进展决策、暂停／保存／停止
及精确句柄回收。抽验前后检查 size／mtime；首轮不一致时主实现和独立实现各重算一次，
只有双方恢复到原摘要才记为偶发恢复，否则以 `verify_hash` attempt 和 unstable 当前哈希
留证。

## 十、测试环境与防干扰方案

### 10.1 测试根

每次运行建立：

```text
.test_runtime/
└── v1_6_0/
    └── <run-id>/
        ├── temp/
        ├── fixtures/
        ├── outputs/
        ├── tools/
        └── logs/
```

运行包装必须：

- 验证解析后的绝对路径位于工作区；
- 设置 `TEMP`、`TMP`、`TMPDIR` 到 `temp`；
- 设置 `PYTHONDONTWRITEBYTECODE=1`；
- 向项目代码传入明确的 fixture／output 路径；
- 清理前再次验证只删除本次 run-id 目录；
- 失败时可选择保留该 run-id 供诊断，但不得污染正式 `Output`。

### 10.2 外部工具替身

在 `tools` 下生成受控替身，模拟：成功、warning、unsupported、损坏、超时、永久阻塞、
异常退出、无输出、超长输出和版本变化。替身只读取 fixtures，所有子进程句柄由测试对象
持有。不得调用系统中正在工作的 ExifTool、ffprobe、7-Zip 或其它 DAISY 进程。

### 10.3 GUI 测试

- 优先控件状态、几何、可达性和事件断言，截图只作辅助；
- 真实 Tcl/Tk 窗口使用自动关闭和独立工作区测试根；
- 不打开文件资源管理器、浏览器或外部 Excel；XLSX／HTML 用结构解析验证；
- 一个测试窗口只终止自己创建的子进程；
- 失败也必须在 finally 中回收本窗口句柄，但不得扫描系统进程寻找遗留项。

## 十四、发布阻断条件

以下任一项未满足，不得发布 v1.6.0：

1. 任一封存库消费者不能读取合格 v1.4.1／schema 3 金样；
2. 任一旧库测试前后 SHA-256 改变；
3. 一次完成与续传在非白名单业务字段上不等价；
4. 永久阻塞 worker 无法由精确句柄回收，或会影响其它进程；
5. 默认无人处置时会静默跳过文件；
6. unsupported 被列成逐文件问题，或真实已知格式损坏被宽泛隐藏；
7. Issues 把未执行／未记录的板块写成 0 或“通过”，而不是 `NULL`；
8. Full 默认关闭格式校验时不再保持基线含义；
9. 跨版本 Diff 把缺失能力误判为变化或一致；
10. 核验用 stat 相同冒充内容哈希一致；
11. 数据库解析仍整表 `fetchall()`、覆盖旧报告或无法导出 raw payload；
12. HTML／XLSX 存在内容执行、公式注入或打开失败；
13. GUI 任一规定尺寸／字号组合存在不可达控件、无意义滚动、文本消失或 TclError；
14. 测试访问工作区外项目数据、真实硬盘或影响其它运行进程；
15. `TEMP\`、测试运行目录、真实数据库或私人路径进入提交；
16. 文档、代码、版本、schema 和实际测试结果不一致。

## 十五、计划自我审查

### 15.1 范围审查

本计划范围很大，不能作为一个不可拆分的大提交实施。Reader、行为保持型重构、schema、
worker、核验、Diff、解析和 GUI 必须分别形成可回滚检查点。先建立兼容层再改 schema，
否则一旦旧库读取失败，很难判断是 schema、SQL 还是 UI 回归。

结论：使用 v1.6.0 合理；必须分阶段，不接受“一次性重写”。

### 15.2 “全部兼容 v1.4.1”的可实现边界

旧库没有未来 format checks、attempt 或性能表，无法展示它从未记录的事实。正确兼容是
功能可运行并诚实显示能力缺失，不是编造新证据。v1.4.1 partial 不是封存事实库，直接
跨契约续传风险高，因此单独排除并提供安全诊断／复制方案。

结论：封存快照和 Diff 的所有读取功能必须兼容；缺失能力降级；partial 不盲目兼容。

### 15.3 动态 timeout 风险

按每 9 GiB 增加 90 秒用于“无进展”很保守，超大文件可能得到很长等待时间。用户已经
确认这一规则，因此不擅自增加隐藏上限；GUI 必须在开始前和卡住时显示实际秒数，高级
设置允许明确调整。持续有进展时绝不因总耗时触发。

结论：公式照办，但通过可见性、配置验证和受控 worker 避免变成不可解释的长时间卡死。

### 15.4 默认继续等待风险

无人处理时继续等待意味着任务可能无限持续，这是有意选择的证据优先策略。不能把它描述
成“已经解决卡死”；真正改进在于任务不再锁死 GUI，用户可随时跳过或安全停止，且高级
设置可预授权其它动作。

结论：默认不丢数据；UI 必须持续响应并显示状态。

### 15.5 Full 集成格式校验风险

ZIP CRC、7-Zip 测试和媒体结构检查可能再次读取大量数据，显著增加时间和介质负载。如果
默认开启，会改变 Full 的用户预期和基线性能。因此默认关闭，Quick 禁止，启用时明确
显示额外读盘成本并单独记录覆盖。

结论：作为 Full 附加项可行，但不能假装无成本，也不能删除旧快照的独立底层复核能力。

### 15.6 unsupported 过滤风险

若按“所有解析失败”宽泛过滤，会隐藏已知格式损坏。本计划只过滤明确归一化的
unsupported／unknown／unrecognized format；MP4 缺流、JPEG format error、truncated、
timeout 和工具崩溃仍报告。

结论：只计总数的对象必须是确定性能力不支持，而不是所有失败。

### 15.7 数据库解析范围风险

HTML 不能承载几十万行，XLSX 有行数和单元格限制，raw JSON 不适合 CSV 平铺。因此人读
HTML 只做摘要和 200 行预览，XLSX 做筛选，CSV 做平面技术字段，JSONL 做嵌套和 raw。
SQLite 继续是完整事实来源。

结论：按数据形态选择格式，不承诺一种格式适合所有模块。

### 15.8 脚本合并风险

直接把 31／32／41 合成一个巨大脚本会降低可维护性。正确的“合并”是统一用户入口、
编排、Reader、状态和 writer，同时保留小而稳定的兼容包装。共享逻辑进入 Lib，Module
保持薄。

结论：减少重复实现，而不是机械减少文件数量。

### 15.9 新 schema 与旧程序

若 v1.6.0 使用新 schema，v1.4.1 程序通常无法理解它。不能同时承诺“新增强语义表”和
“旧程序读取新库”。本计划保证 v1.6.0 读取 v1.4.1 旧库，并在新库 manifest 中诚实提高
最低读取器要求。

结论：后向读取兼容是硬门槛，反向前向兼容不虚假承诺。

### 15.10 测试现实性

在不读取真实档案、不检测真实硬盘且不影响现有进程的约束下，可以充分验证状态机、
兼容、格式、输出、安全和 GUI，但不能证明所有真实 USB 桥、坏扇区或设备固件行为。
发布说明必须如实写出这一边界；如以后需要真实硬件试验，必须另行取得明确授权并使用
隔离设备，不能混入本计划的自动测试。

结论：合成测试是当前正确方案，但不能夸大为所有硬件环境实证。

## 十七、完成定义
