## 一、设计原则

1. 源档案始终只读；超时、重试、跳过和停止都不能修改源文件。
2. 默认策略偏向证据完整，不得为了“任务能结束”而静默跳过卡住或失败的文件。
3. 每次恢复、工具切换、重试、超时与人工决定都必须可审计。
4. 已封存数据库保持不可变；续传只作用于明确的运行态产物。
5. “可续传”由独立的数据契约决定，不再简单等同于应用版本号相同。
6. 一次扫完与中断续传比较业务语义，不比较 UUID、时间、事件序列、row ID、SQLite
   页布局或最终文件哈希。
7. 涉及新增状态、尝试记录或证据表时，必须明确评估并升级 schema；不得在旧 schema
   下悄悄改变字段含义。
8. v1.6.0 必须继续只读使用 v1.4.1 已封存 schema 3 数据库，不原地迁移、不回写；
   新程序读取旧库是发布硬门槛，旧程序读取未来新 schema 不作反向承诺。
9. 所有测试、夹具、输出和临时文件都限制在工作区内；不读取真实档案、不运行真实硬盘
   检测，不枚举、终止、挂接或复用其它正在运行的进程。

## 三、续传状态机方案要求

### 3.1 契约与身份

- 应用版本、SQLite schema、元数据 profile、文件名布局和续传契约分别记录，不能互相
  代替。只有经过测试并列入兼容矩阵的组合才允许恢复。
- roots、哈希模式、元数据范围、File ID 策略、抽验比例、增量来源、root 映射、输出
  目录和发布 stem 必须区分“不可变身份参数”与“恢复时可替换运行参数”。
- 工具路径可以因机器变化重新发现，但必须记录每次发现结果；是否允许跨工具版本继续，
  需要明确策略，不能只依赖最终 manifest 覆盖说明。

### 3.2 阶段与封存

- 至少能区分运行、已中断、正在封存、封存完成但未发布、已发布和不可恢复失败。
- 完整性检查失败、最终目标冲突、Issues 报告创建失败或原子发布失败后，不得留下
  “状态 complete 但既不能发布也不能续传”的孤立 partial。
- 重新枚举全部 root 目前是正确性优先的安全默认值。任何快速恢复方案都必须证明不会
  漏掉暂停期间的新增、删除、改名或状态变化，不能只依靠保存的阶段编号跳过对账。
- 每次恢复应记录 session ID、开始／结束时间、结束原因、使用工具和处理条目范围；
  快照级开始时间、累计活动时间和跨中断墙钟时间必须能被明确区分。

### 3.3 重试与变更失效

- 确定性“格式不认识”诊断不应无意义重复；I/O 错误、超时、工具崩溃等瞬时失败应可按
  用户策略重试。
- 重试前必须清理该条目上一次尝试的派生行，同时保留独立的历史尝试证据，避免旧错误
  与新成功结果混在同一当前状态中。
- 普通恢复至少综合 size、mtime、File ID／卷身份等现有证据；严格恢复模式应允许重新
  哈希中断前已完成的文件。对无法可靠识别的同 size／mtime 内容变化必须在 UI 和报告
  中明确边界。

### 3.4 暂停、停止与跨重启继续

- “暂停／继续”用于窗口仍打开的同一次运行：暂停后不再领取新的工作单元，当前操作在
  可验证的安全边界停下，进程、任务身份和锁仍保留；继续时不创建新的恢复任务。
- “保存进度并退出”是可跨关机的持久化暂停：提交已完成工作，记录暂停原因与阶段，
  关闭 SQLite 和本窗口创建的工作进程并释放锁。下次启动 DAISY 时显示恢复卡片和风险
  摘要，由用户确认后继续；不得仅因发现 partial 就自动读取源文件或启动扫描。
- “停止任务”表示用户结束本次任务意图。为避免误删证据，partial 默认仍保留，但标记
  为已停止且下次启动不主动建议恢复；用户仍可从续传入口手动选择或明确删除。暂停、
  保存退出与停止可以共用安全收尾机制，但状态、事件、默认入口和用户意图不能混写。
- 运行中关闭窗口仍必须确认，首选项为“保存进度并退出”；系统关机通知只能作为尽力
  保存的机会，正确性不得依赖操作系统一定给予足够时间。突然断电或进程被杀后也必须
  能依靠 SQLite 事务和恢复审计回到一致状态。
- 不持久化 Python 哈希对象或外部工具的进程内部状态。跨重启时保留已完成文件；中断时
  正在哈希或解析的单个文件回到可重试状态并从头处理，避免把不可验证的中间摘要当成
  完成证据。同会话暂停是否保留当前文件内存状态必须单独测试，不能影响跨重启结果。
- 本功能指“下次打开 DAISY 后可继续”，不默认配置 Windows 开机自启动，也不自动开始
  读取。若未来增加开机自启动，必须作为独立、默认关闭的设置设计。

## 四、哈希 stall 与超时方案要求

### 4.1 检测和默认策略

- 继续保留短周期 stall 告警，用于提示“读取没有进展”，但 stall 与 timeout 必须是
  两个不同概念。
- 超时基于“最后一次成功读取数据的时间”，而不是整个大文件的总处理时间。
- 默认无进展超时参考 ExifTool 的分级设计，按枚举阶段登记的 `size_bytes` 计算：
  `max(90, ceil(size_bytes / (9 × 1024³)) × 90)` 秒。恰好 `9 GiB` 为 90 秒，超过后
  进入下一个 90 秒阶梯；该值是连续没有成功读取新数据的时间，不是整个文件的总哈希
  时限。每次成功读取数据块都会重置无进展计时。
- 当前 30 秒阈值继续只产生早期 `stall` 告警，不直接取消读取。达到分级 timeout 后才
  进入工作进程回收和用户策略；“继续等待”重新开始当前文件的有效等待窗口并留下事件。
- 阈值及 9 GiB／90 秒阶梯必须可配置并进入运行配置和事件证据；记录文件体积、实际
  采用秒数、最后成功偏移和触发时间。配置边界值必须验证为正数并采用明确的 ceiling
  语义，不能因整数截断缩短等待时间。

### 4.2 隔离、停止与继续

- 单文件读取应在独立工作进程中执行。控制进程负责心跳、进度、软停止、超时升级和
  最终强制回收；不能假设阻塞线程可以在 Windows 上可靠取消。
- 超时后默认不得伪装成成功或普通 skipped。记录文件、已读字节、停滞秒数、阈值、
  尝试编号、结束原因和用户选择，再按明确策略进入下一文件或停止整次任务。
- 达到无进展阈值先记录 `threshold_reached`，不等同于该文件最终失败。默认自动处置为
  “继续等待”：工作进程保持运行，GUI 显示“继续等待”“跳过并记录”“停止并保留续传”，
  用户不操作时不会静默跳过或停止；若读取后来恢复，文件仍可正常完成，但阈值事件保留。
- 高级设置提供“无进展超时自动处置”，可选“继续等待”（默认）、“跳过并记录”和
  “停止并保留续传”。非默认策略必须在任务开始前显示后果并写入本次运行配置；选择
  自动跳过时还须在保存设置时明确确认，不能把历史设置变化当成本次人工点击。
- 自动处置和用户点击必须通过同一原子决策状态，确保只执行一次。用户选择“继续等待”
  后重新开始该文件的有效等待窗口；“跳过并记录”终止并回收当前文件工作进程，记录
  timeout 而非普通 skipped；“停止并保留续传”先回到一致事务边界再结束 session。
- “停止并保留续传”必须先让 SQLite 回到可恢复事务边界，并只终止本窗口创建的工作
  进程，不能按进程名影响其他 DAISY 窗口或外部进程。

### 4.3 GUI 行为

- stall 状态显示完整文件路径、文件大小、已读字节、最后进展时间和累计停滞时间。
- “继续等待”只延长当前尝试；“跳过并记录”必须二次确认并产生明确 issue；“停止并
  保留续传”结束本次 session，但不删除 partial。
- GUI 必须在开始前展示动态阈值和高级设置中的自动处置。默认继续等待时，未操作的
  决策界面不得阻塞 Tk，也不得重复弹出窗口；持续更新停滞时间即可。自动跳过或停止时
  必须在日志和进度区显示所采用的预设策略，不得表现成用户刚刚点击。
- 顶部「视图」或「设置」增加默认关闭的“显示当前文件”开关。开启后，在当前阶段
  进度条的紧邻位置使用独立单行标签显示：枚举阶段为当前目录，哈希、元数据、复扫和
  抽验阶段为当前文件。不要把文字直接绘制在主题进度条色块内部。
- 显示值应使用可区分重名文件的相对路径；窄窗口中间省略，悬停可查看完整路径。
  小窗与普通界面共享同一状态；完成、停止或切换任务后清空，stall 时保留并突出显示。
- 生产者合并并限频发送 `current_item` GUI 事件，目标更新频率不高于 5～10 Hz；不能
  对每个小文件无条件刷新 Tk 或写日志。开关关闭时，后端停止发送文件名事件，而不是
  只隐藏标签。普通当前文件状态默认不写日志或数据库，stall、错误和人工跳过仍按审计
  规则持久化。
- 数值进度建议保持约 1～2 Hz，并由生产者按时间合并最新字节数、条目数和错误数。
  哈希每个数据块更新内存计数但只限频发送；枚举、元数据、复扫和独立抽验接入同一
  协议。GUI 事件轮询可保持约 80 ms，但每类只应用最新状态，避免积压。
- 不确定进度动画不是数据进度。现有 12 ms 动画步进应评估放宽到约 30～50 ms，减少
  无意义重绘；任何调整必须通过多窗口、三级字号和不同 DPI 下的流畅性与 CPU 对比。

### 4.4 事后性能诊断

- 为实际读取的文件保存单调时钟总耗时，并以受控频率记录进展摘要；至少能够还原
  `bytes_read`、stall 次数、最长 stall、首次／末次 stall、最终读取偏移和结束原因。
  不应把每个 4 MiB 块都无条件写入 SQLite，以免遥测本身显著放大数据库和 I/O。
- 自动分析必须排除 `origin=reused`，并在同一卷、相近文件大小和相近文件类型内使用
  中位数、MAD 或分位数识别离群值；不得用一个全局 MiB/s 阈值比较小文件与大文件。
- 报告结论使用“可疑逻辑路径／读取时段”，不能仅凭吞吐宣称物理坏区。杀毒扫描、
  系统缓存、并发 I/O、文件碎片、USB 桥重试和设备降速都可能产生相同表现。
- 若需要分析逻辑磁盘区域，应单独评估 Windows 只读文件 extent／卷 extent 查询，记录
  查询能力与失败原因。即使取得逻辑 LBA，SSD 的控制器映射、垃圾回收和磨损均衡仍使其
  不等于物理闪存位置；机械盘也可能存在控制器重映射。
- 达到既定可信阈值的候选项必须进入最终数据库同目录、同基名的 `_Issues.md`，章节名
  固定为“读取性能异常候选”。即使没有其它源文件、哈希、元数据或枚举问题，只要存在
  这类候选，也应生成同一份 `_Issues.md`；不得另建一个相互竞争的性能问题报告。
- “读取性能异常候选”至少列出 root、相对路径、文件大小、单调时钟耗时、平均吞吐、
  比较组定义、组内中位数／分位数、偏离比例、stall 次数、最长 stall、session 和判定
  规则。报告必须明确写出“需要人工复核，不能据此认定物理坏区或设备故障”。
- 未达到可信阈值的原始样本和低置信度离群只保留在数据库证据中，不制造 Issues 噪声；
  `_Issues.md` 可限制明细行数，但必须显示候选总数并说明完整证据所在表／事件。报告
  渲染不得删除、改写或降级 SQLite 中的原始性能记录。
- 性能异常与 `has_file_issues`、`has_unstable_entries`、`has_enumeration_gaps` 是不同
  语义。优先设计独立的 `has_performance_anomalies` manifest／状态能力；若因此新增字段、
  表或读取契约，按第八节执行 schema 与版本门槛，不能暗改旧状态含义。
- 性能摘要应允许与同一设备的历史扫描基线比较；基线身份必须可靠关联卷与设备，且
  公开 `_Issues.md` 前提示路径、设备标识和性能数据的隐私风险。

## 五、报告、旧库兼容与既有核验要求

### 5.1 Issues.md 人读输出

- 正文按“需要处理”“待复核候选”“信息性诊断”排序，不能让 warning／validation
  分类表出现在实际错误之前。汇总使用文件数表达处理规模，布尔值只用于机器状态。
- 报告使用固定 Markdown 二级标题分为枚举、哈希、Exif／元数据、格式校验、读取性能
  候选和运行／证据等板块。每个板块已执行且无问题写 `0`；本次未执行、旧库未记录或
  能力不适用写字面值 `NULL` 并说明原因，不能用 `0` 或“通过”代替未知。
- 确定性的“不支持／无法识别文件类型”不列为错误或待复核明细，不显示路径、扩展名
  分组或逐条诊断，只在汇总中记录去重后的文件总数；如果它们是唯一诊断，不单独生成
  `_Issues.md`。原始状态、错误与诊断仍完整保留在 SQLite，供审计和结构化导出使用。
- 上述过滤只适用于明确归一化为 unsupported／unknown／unrecognized format 的确定性
  诊断。已知格式的容器损坏、缺少媒体流、截断、解析 timeout、工具崩溃和读取错误仍是
  问题或待复核候选；不得把所有“解析未成功”宽泛隐藏。
- `ExifTool:Main:Copy1:Warning` 等动态序号必须在报告分组时归一化为稳定字段族；本次
  实测的 2,697 个原始分类归一化后应收敛为 12 个，不得按 `CopyN` 展开数千行。
- 每个汇总同时显示诊断记录数和去重后的影响文件数。validation 表示元数据质量或占位
  值检查，不等同于文件损坏；普通 `[minor]` warning 和 validation 默认折叠。
- 不能无条件丢弃 warning。包含格式损坏、读取中止、截断或同一文件异常高密度 warning
  的条目进入保守的“待复核候选”，规则必须通过正反夹具验证，不能只按英文单词做宽泛
  子串匹配。完整诊断继续保留在 `metadata_diagnostics`。
- 合并重复的“问题条目状态”和“错误明细”，同一条显示路径、错误码、元数据／哈希
  状态及建议操作。同拍摄组聚合只能作为展示层推断，并保留展开后的逐文件证据。
- 所有折叠章节显示总数、已展示数和完整证据所在表；报告生成前后逐表验证 SQLite 未被
  修改。v1.4.1 旧库使用新报告器渲染时也必须满足同一人读输出契约。

### 5.2 DBS-41 数据库解析

- 功能定位拆为两层：“人读报告”回答数据库是什么、是否完整、包含什么、哪里需关注和
  两次快照有何变化；“技术数据导出”提供完整、稳定字段供脚本、审计和二次分析。不得再
  把完整表格转存本身称为人读报告。
- GUI 只保留一个“选择数据库”入口。选择后在后台以只读方式识别快照／Diff 类型、
  schema、生成器版本、封存状态、数据库大小、可用模块和各模块行数；用户不再手工选择
  输入类型。识别失败必须说明缺失能力，不能以 SQLite 异常堆栈代替提示。
- 交互参考物理硬盘页：识别时展开进度与日志；识别成功后弹出结果提示，展开设置并收起
  进度／日志，显示统一尺寸的模块复选卡；点击导出后再次收起设置并展开进度／日志。
  “全选／取消选择”保持紧凑，页面无真实溢出时不得出现可滚动空白。
- 快照能力至少拆为：概览、Issues、文件／目录、内容哈希、照片元数据、视频元数据、
  GPS、媒体流、工作文件、文档、压缩包／成员、错误／诊断、运行事件／manifest。
  Diff 能力至少拆为：概览、文件变化、目录变化、内容多重集、枚举缺口和证据说明。
  无表、无列或零行模块必须明确显示“不可用”或“无记录”，不能让导出阶段才失败。
- 提供“人读摘要”（默认）、“完整审计数据”和“自定义”预设；用户仍可逐项勾选。
  输出格式独立勾选为：自包含 `Report.html`（人读默认）、`Report_Excel.xlsx`（筛选分析）、
  完整技术 CSV（脚本／审计）及 JSONL（嵌套／原始数据）。Markdown 只承担 Issues、
  纯文本摘要或便于版本管理的内容，不再负责承载完整大表。
- `Report.html` 不依赖网络或 CDN，全部文本 HTML 转义，使用本地内嵌 CSS／必要的最小
  脚本；包含目录、结论卡片、数量与容量汇总、问题优先区、可折叠章节、表内筛选、打印
  样式和窄窗口响应布局。大表只展示明确上限的预览并标出总数和完整数据出口。
- XLSX 首页必须是中文概览而不是 CSV 使用说明；保留冻结表头、筛选、合理列宽、超行
  自动分表和 Unicode。技术 CSV 继续保持 UTF-8 无 BOM、LF、原字段名与完整值，并明确
  标为机器接口；任何人读入口不得要求 Excel 猜测 CSV 编码。
- 所有大表使用流式游标导出，不得 `fetchall()` 整表进入内存。数据库检测、导出和取消
  都必须显示阶段和已处理行数；先写工作区内临时目录，成功后 no-clobber 原子发布，
  失败或取消不覆盖旧报告，也不把半成品目录伪装成成功结果。
- HTML／XLSX／CSV 必须防止公式注入、非法 XML／HTML 字符和超长单元格造成打开失败；
  完整原值不能因人读格式限制而从技术数据中丢失。报告公开分享前继续提示路径、设备和
  元数据隐私风险。

### 5.3 v1.4.1 数据库兼容契约

- “兼容 v1.4.1”明确指 v1.6.0 程序可读取 v1.4.1 生成的完整 schema 3 快照，并可用于
  Issues 渲染、DBS-21、DBS-31、DBS-32 和 DBS-41；不要求 v1.4.1 程序反向理解未来
  v1.6.0 新 schema、状态或表。
- 旧库一律使用 SQLite 只读连接，不执行 `ALTER`、迁移、补列、VACUUM、journal 模式
  切换或任何回写。每项兼容测试在执行前后计算整个数据库 SHA-256，并断言字节完全一致。
- 建立不含私人路径的固定 v1.4.1 schema 3 金样夹具，覆盖 Full、Quick、无哈希、错误、
  unsupported、unstable、枚举缺口、重复内容和元数据缺表／空表边界。工作区 `TEMP` 中
  的用户旧库只允许额外只读审计，不纳入测试依赖，也不得修改、复制进提交或访问其记录
  指向的外部路径。
- 新旧 schema 通过统一只读能力描述转换为稳定的内部投影。旧库没有的新字段使用明确的
  “不可用”语义，不能伪造为 0、成功或空字符串；跨版本 Diff 必须区分“证据不存在”和
  “证据证明没有变化”。
- 兼容矩阵至少覆盖 schema 3→schema 3、schema 3→v1.6.0、新 schema→schema 3 和新
  schema→新 schema；输入顺序互换后的方向性状态应符合定义。任何消费者新增必需表列
  时，都必须同时提供旧库 fallback 或明确从 v1.6.0 范围撤回该能力。

### 5.4 DBS-21／31／32 重新审计

- DBS-21：验证相同库自比、旧旧、旧新、新旧和新新组合；覆盖 root 自动／显式映射、
  added／deleted／moved／copied、同哈希多重集、硬链接、hash_missing、unstable、枚举
  失败子树、raw payload 缺失和 metadata extraction 变化，确保内容与结构结论不串扰。
- DBS-31：核验前后都读取 size／mtime，只有两次稳定且读取字节完整时才能形成有效独立
  结论；接入 v1.6.0 哈希工作进程、暂停、动态无进展 timeout 和三种处置策略。旧库没有
  基准哈希时明确显示不可核验，不把 stat 相同表述为内容一致。
- DBS-32：按格式维护可解释的校验能力表和实测夹具；unsupported 只计总数，已知格式
  损坏、截断、缺流、CRC 错误、工具 timeout／崩溃仍进入问题。ExifTool、ffprobe、7-Zip
  的超时、退出码、版本差异和长路径必须分别测试，不以一次外部工具成功代替深度解码。
- 三个模块的结果均需提供面向人的结论、口径、覆盖率、证据不足和建议操作，同时保留
  稳定机器输出；输出命名、取消、no-clobber、部分失败和 GUI 进度行为与 DBS-41 对齐。

### 5.5 DBS 信息架构与格式校验整合

- 普通用户只看到四个 DBS 入口：“扫描”“对比”“核验”“解析”。DBS-11／12／21／31／
  32／41 继续作为代码、CLI、日志和技术文档中的稳定编号，现有命令不因 GUI 合并而删除。
- “扫描”先选择“完整扫描（Full）”或“快速扫描（Quick）”，再展示该模式可用的功能。
  Full 的既有含义保持为完整内容哈希、完整元数据和 File ID；新增格式校验只是附加能力，
  默认关闭。Quick 继续不读取内容、不运行外部解析工具，格式校验在 Quick 下不可选并
  显示原因，不能启用后仍称为 Quick。
- Full 的“格式校验”选项为“关闭（默认）”“抽样校验”“全部校验”。启用后使用与独立
  核验相同的底层服务、判据、timeout 和工具溯源；unsupported 只计总数，真实 invalid、
  missing、timeout 和工具失败进入 Issues，但不因存在问题阻止快照完整封存。
- “核验”选择一份封存快照并映射当前根目录，基础 stat 核对始终执行；用户可独立勾选
  “内容哈希”和“格式校验”。因此既有 v1.4.1 快照仍能重新检查格式，而 GUI 无需保留
  单独的“文件结构核验”入口。
- “对比”选择基准与对比快照后自动识别双方 schema、生成器和证据能力，必须支持
  v1.4.1↔v1.4.1、v1.4.1↔v1.6.0 以及 v1.6.0↔v1.6.0；方向互换不能沿用旧缓存或
  混淆 added／deleted。缺少新字段时降级证据，不把缺失能力判为变化。
- “解析”采用[数据库解析设计](Spec_DAISY_V1_6_0_Database_Parsing_Design.md)：选择
  数据库后自动识别模块，再勾选逐文件哈希、格式化元数据、原始载荷等内容和
  HTML／XLSX／CSV／JSONL 格式。
- 快照默认关闭格式校验时继续沿用 `根标签_Full_日期_时间_XXXXXXXX.sqlite`，保证
  Full 基线名称不变。抽样或全量格式校验可分别增加 `Fmt-Sample`／`Fmt-All` 能力标记，
  精确抽样比例和校验规则以 config／manifest 为准；新标记必须使用新的
  `filename_layout_version`，读取旧 v1.4.1 文件时不得依赖该标记判断库内能力。

## 六、验收测试

v1.6.0 至少通过以下合成测试；默认不读取真实档案、不运行真实物理硬盘检测，也不影响
其它正在运行的进程：

1. 同一固定夹具分别一次扫完，以及在枚举、哈希、元数据、复扫和封存前中断后续传；
   对业务语义投影逐表比较，允许的差异只来自明确白名单。
2. 暂停期间分别新增、删除、改名、改变 size／mtime、只改变内容但恢复 size／mtime，
   验证普通与严格恢复模式的结果和风险提示。
3. 未处理、遗留 processing、瞬时 error、确定性格式诊断、timeout、unstable 和已完成
   条目按三种重试策略执行，验证当前结果与历史尝试不会混淆。
4. 初次运行和恢复使用相同工具版本、升级工具版本、工具缺失和显式工具路径四种组合，
   验证每条派生证据可追溯到实际 session。
5. 默认输出目录、自定义输出目录、输出目录位于 root 内三种组合，确认恢复时始终排除
   正确的本次产物目录。
6. 同机活锁、同机死锁、损坏锁、异机锁和 PID 复用夹具，验证不会错误接管。
7. 完整性检查失败、最终目标冲突、Issues 目标冲突和原子发布失败后，验证 partial 可按
   状态继续封存或安全导出，不会覆盖旧产物。
8. 构造完整、截断尾行和中段损坏的事件流，验证证据保留、诊断和封存策略。
9. 使用受控工作进程模拟持续进展、短暂停顿后恢复、永久阻塞、读取异常和用户停止，
   验证没有僵尸进程、数据库事务残留或跨窗口误终止。
10. 在 GUI 中验证续传预览、stall 操作、关闭确认、独立日志、小窗往返和任务结束后的
    面板状态；所有长路径和倒计时文字在既有字体／字号／尺寸矩阵中完整可达。
11. 以大文件、小文件、不同受控延迟和并发噪声夹具验证性能统计；自动结果应命中注入的
    慢逻辑路径，并避免把增量复用、小文件固定开销或单次短暂停顿误报成物理坏区。
12. 在开关关闭／开启、小窗／完整界面、三级字号和长中文路径下验证当前文件状态；
    关闭时不得产生 `current_item`，开启时限频、无事件积压、文字可达且不进入普通日志。
13. 分别用少量慢文件、大量小文件、单个超大文件和慢复扫／抽验夹具验证进度：数值

## 七、完成定义

只有在上述高优先级项目已实现、技术规格更新、迁移／兼容决策明确、目标测试和完整回归
通过，并且实际产物可以解释每次恢复与超时决定时，才能把这些项目从“待办”改为
“已完成”。仅增加 GUI 计时器、日志告警或自动重试，不视为解决哈希卡死与续传一致性。

## 八、影响分级与版本门槛

本待办全部落地时，不再属于“只改续传或 UI”：

| 变更组 | 扫描实现影响 | 封存数据库影响 |
|---|---|---|
| 当前文件开关、GUI 事件限频、动画刷新 | 仅增加瞬时事件；关闭时不发送 | 应保持无影响 |
| 按块字节进度、枚举／复扫／抽验进度 | 增加限频回调和少量运行开销 | 不持久化时可保持业务语义不变 |
| 单文件哈希工作进程隔离 | 重写读取、停止与回收边界 | 正常成功路径应等价；错误／中断行为会改变 |
| timeout、人工跳过和失败重试 | 改变扫描控制流与处理集合 | 改变状态、errors、Issues、统计和封存结果 |
| run session、尝试历史、工具溯源 | 改变运行证据模型 | 可能新增表或扩展 data contract |
| 性能摘要与慢路径分析 | 增加扫描遥测 | 写入库时改变内容；新增结构时必须评估 schema |
| 失效判据与严格恢复 | 改变恢复时重新处理的文件集合 | 可能改变续传结果 |
| 锁、输出目录和封存状态机 | 改变启动、目录排除和发布流程 | 可能改变纳入文件及 partial／final 状态 |
| 暂停、保存退出与停止语义 | 改变任务控制、锁释放和恢复入口 | partial 状态／事件会改变；最终成功业务投影应等价 |
| Issues 人读重排与诊断折叠 | 只读查询和报告渲染改变 | SQLite 原始记录、状态和 schema 应保持不变 |
| v1.4.1 读取适配层 | 改变所有数据库消费者的准入和投影 | 旧库始终只读且字节不变；新库 schema 可独立升级 |
| DBS-21／31／32 重新审计 | 对比与核验控制流可能改变 | 输入数据库只读；新生成 Diff／报告语义可能升级 |
| DBS-41 数据库解析 | 改变 GUI、查询、格式、脚本职责和发布流程 | 输入数据库只读；只新增可重建解析产物 |
| 四入口信息架构 | 组合既有 CLI 服务并改变 GUI 状态流 | 不因页面合并改变旧库或既有命令契约 |
| Full 可选格式校验 | 增加默认关闭的读取阶段和工具调用 | 关闭时业务投影保持基线；开启时新证据需明确版本化 |

本轮已确定命名为 v1.6.0，可以为新的状态、尝试历史和性能证据升级 schema，但不得只为
维持 `schema_version=3` 而把新语义不透明地塞入既有 `errors` 或
`run_events.payload_json`。任何升级都必须同时交付 schema 3／v1.4.1 只读适配层、跨版本
Diff 投影、读取兼容矩阵和迁移边界说明；不得以“这是 major/minor 版本”降低旧库兼容要求。
